Two issues were found and corrected before a successful apply: (1) the first apply attempt failed at statement 0 with `function uuid_generate_v4() does not exist` — a targeted read-only diagnostic found the migration-apply connection's search path doesn't include the `extensions` schema (where `uuid-ossp` lives), while `gen_random_uuid()` (native `pg_catalog`, and already the convention used by `studios.id`) resolves regardless; both `id` defaults were switched to `gen_random_uuid()`. (2) Retry-safety hardening added a `DROP POLICY IF EXISTS` before each of the 8 `CREATE POLICY` statements, since Postgres has no `CREATE POLICY IF NOT EXISTS` and the file's transaction/atomicity behavior under the CLI could not be verified from official documentation.

Post-apply read-only verification confirmed: `0030` shows applied in migration history (local/remote match); `partners` and `event_credits` exist; `events.published_credits` exists and is nullable; all 5 new indexes present including both uniqueness rules; RLS enabled on both new tables; exactly 4 policies on each (8 total), no broad/public-access policy on either. `photographers` and `events.photographer_id` remain completely untouched.
