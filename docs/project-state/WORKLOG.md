## 2026-08-10 — Partner / Event Credit Foundational Schema (COMPLETE / PASS)

Ran a bounded, read-only Partner/Event Credit repository preflight before any design work. Found no "Partner"/"Client" entity anywhere in the codebase (schema, generated types, API, UI, tests) — every `partner`/`client` text hit was incidental marketing copy or an unrelated billing plan-tier name. The only real precedent was the legacy `photographers` table (studio-scoped, RLS since migration `0003`, but with no `CREATE TABLE` anywhere in tracked migration history — it predates the migrations folder) and its single-credit `events.photographer_id` FK, already wired end-to-end into `eventContract.ts` (legacy layer only) and the shared `weddingTemplateRenderer.ts`/render Worker footer, but entirely unwired from the newer canonical `CanonicalEventRecord`/`PublicEventConfig`/Draft Preview path (which passes `photographer: null`). This matched the Baseline V2.1 gap map's REPAIR classification, not a greenfield build.

Because `photographers`' exact live shape was unverifiable from code alone, a targeted read-only live-schema preflight (`supabase db query --linked`, scoped strictly to `photographers` and `events.photographer_id`) was run before any migration was authored. It found live schema drift beyond the tracked migrations: two dead/unreferenced columns on `photographers` (`studio_name`, `phone`), a **global** (not studio-scoped) unique constraint on `phone_number`, no index on `studio_id`, and — most significantly — **two undocumented RLS policies not present in any tracked migration**: `Admin full access on photographers` (ALL, for any authenticated user regardless of studio) and `Public can view photographers` (SELECT, unrestricted/anonymous). This is a real, live cross-tenant/public-exposure security finding on the legacy table. It was **flagged as a separate follow-up and deliberately not fixed or touched** in this task — out of scope for a schema-foundation slice.

Designed local migration `eventcast-admin/supabase/migrations/0030_partner_event_credit_foundation_schema.sql`, purely additive: new `partners` table (studio-owned master identity, public-safe fields plus one private `internal_notes` field, no phone-uniqueness carried forward, indexed on `studio_id`, 4 tenant-scoped RLS policies deliberately not reproducing the two undocumented legacy policies above), new `event_credits` join table (editable event-to-partner references, `role_label`, `is_primary`, one-primary-per-event via a partial unique index, tenant isolation fully database-enforced via `EXISTS` joins through `events`/`studio_members` with no redundant `studio_id` column, insert/update additionally requiring the referenced partner's `studio_id` to match the event's), and a nullable, unused `events.published_credits jsonb` column reserved for the future Publish task's frozen snapshot. `photographers` and `events.photographer_id` were left completely untouched.

The design went through several rounds of narrow, read-only-first review before application:

1. **SQL review** — verified tenant isolation on all 4 RLS verbs independently (including that `UPDATE` correctly uses both `USING` and `WITH CHECK` to block repointing a credit to a foreign event or partner), verified the partial unique index and Postgres/Supabase syntax, and found one real gap: nothing prevented an exact duplicate `(event_id, partner_id, role_label)` row. **REVISE** — added a second unique index on that triple; re-reviewed and accepted.
2. **Migration-application preflight** — `supabase migration list --linked` and `db push --linked --dry-run` confirmed `0030` as the sole pending migration with no divergence in `0001`–`0029`. Separately, the file's transaction/atomicity behavior under `supabase db push` could not be verified from the installed CLI's help output or official Supabase documentation (both checked). Given the file's 8 non-idempotent `CREATE POLICY` statements (Postgres has no `CREATE POLICY IF NOT EXISTS`), this was assessed as materially unsafe for a clean retry after any partial failure — **NOT READY FOR APPLICATION**.
3. **Retry-safety hardening** — added a `DROP POLICY IF EXISTS <name> ON public.<table>;` immediately before each of the 8 `CREATE POLICY` statements (safe here specifically because all 8 policies and both tables are wholly new in this same migration, with no earlier-migration counterpart to collide with). An explicit `BEGIN`/`COMMIT` wrap was considered and deliberately rejected: Postgres has no true nested transactions, and since the CLI's own outer-transaction behavior is unverified, an embedded `BEGIN`/`COMMIT` could interfere with an outer transaction rather than safely nest inside it.
4. **Re-confirmed dry-run** — clean, `0030` still the sole proposed migration — **READY FOR APPLICATION APPROVAL**.

**First apply attempt failed** at statement 0: `ERROR: function uuid_generate_v4() does not exist (SQLSTATE 42883)`. A narrow read-only diagnostic (`pg_proc`/`pg_namespace`, `pg_extension`, `information_schema.columns` on `photographers.id`/`events.id`/`studios.id`, `show search_path`) found `uuid_generate_v4()` exists only in the `extensions` schema (via the `uuid-ossp` extension), and the `db push` apply connection's effective search path doesn't include it — unlike the `db query --linked` diagnostic connection, whose search path does (`"$user", public, extensions`), explaining why earlier read-only checks never surfaced this. `gen_random_uuid()` is native to `pg_catalog` (always resolvable regardless of search path) and is already the convention `studios.id` uses. The failure occurred on the very first statement, so nothing was left behind — confirmed via `to_regclass`/`information_schema` existence checks and `migration list --linked` still showing `0030` unapplied. Corrected both `id` defaults (`partners`, `event_credits`) from `uuid_generate_v4()` to `gen_random_uuid()`; no other line changed.

**Re-ran the full preflight sequence** (sole-pending-migration confirmation, clean dry-run) and, on explicit approval, **applied migration `0030` successfully** via `supabase db push --linked --workdir "D:\Eventcast.pro\eventcast-admin"`. The 8 `DROP POLICY IF EXISTS` guards correctly no-op'd (`NOTICE: ... does not exist, skipping`) on this first real apply.
